## 2026-10-16 Siri、Windows语义动作与UIA边界更新

据此，`.196.0`的受限UIA按钮操作候选只能作为普通白名单应用的低风险补充；优先顺序仍应是小K自有类型化能力、目标应用正式公开的语义API/App Actions、最后才是经用户点名且有严格限制的UIA。消息播报只接受明确授权的Windows Toast来源；应用窗口内提示不等于系统通知，UIA事件也不等于消息正文或业务完成。`.195.0`的v7→v8审批审计迁移完整安全检查137项通过，UIA策略和桌面体验145项通过，但隔离worker探针失败于禁用按钮场景；`.196.0`仅将超宽65同级控件合成案例移到独立窗口并补充错误码，等待完整CI。本轮仍未找到微信Toast/AUMID或个人微信/QQ稳定发送路径，既有R0隐私闸门不变。

## 2026-10-15 18:40 Siri能力边界与桌面自动化项目调研

3. 当系统中有自然收到、且你能辨认来源客户端的近期通知时，点击“只读检查近期微信 / QQ 通知来源”。将显示的应用名、AUMID和计数与Windows通知来源核对；不要向任何联系人或群发送测试消息，也不要把显示名候选当成身份证明。
4. 候选必须经真实Toast来源元数据核实后，才可手工填写相应AUMID。完成这一步仅核实发布者来源，不证明私聊归属、去重、正文格式或本地分析准确率；当前适配器仍把会话归属作为未知并拒绝读取正文。
5. 后续要完成每款至少30条的私聊分析门槛，必须先实现并验证严格失败关闭的微信/QQ会话分类与正文短时处理，再由用户在合适时段逐步验收。未经这项实现和单独启用操作，不得把“来源候选已找到”报告成通知分析已通过。

## 结论

R0 基线核对已完成，两个关键能力闸门尚未通过：

1. 微信/QQ后台通知目前无法可靠判定会话和私聊属性，运行代码因此不会读取通知正文；没有找到可证明不抢前台的个人账号发送路径。消息自动分析与发送不得标为已交付，R4 仍受阻。
2. 现有候选模型与固定代码代理管线的评测均未通过完整发布门槛；当前没有可选为首版可靠编程模型的实测证据。编码代理继续改进前，需冻结一版管线并重新跑完整任务集。

不需要等待这两个问题才开始独立的任务中心、可见状态、取消/恢复和文件/浏览器能力工作。继续推进 R1–R3；R4 消息闭环保持条件式路线，R5 编码发布条件保持未满足。

## 微信与 QQ 能力闸门

已读本机进程版本快照：微信 `4.1.15.13`、QQ `9.9.30.48762-6a73892f`。版本随更新变化，后续验收需重新读取。

### 已有实现

- WPF/MSIX 清单声明 Windows `userNotificationListener` 能力；监控按配置的发布者 AUMID 先过滤，仅处理新增 Toast，并有有界去重队列、权限/锁屏复核和状态反馈。
- 本机身份补充核对（2026-10-08）：`Get-StartApps`返回QQ的`AppID=QQ`、微信的`AppID=D:\微信\Weixin\Weixin.exe`；微软文档说明该命令的AppID就是AUMID。[Get-StartApps](https://learn.microsoft.com/en-us/powershell/module/startlayout/get-startapps) 微信开始菜单快捷方式目标为`D:\微信\Weixin\Weixin.exe`（4.1.15.13），QQ快捷方式目标为`D:\QQ\QQ.exe`（9.9.30.48762）；两个可执行文件的签名均有效，发布者为Tencent。Windows通知设置注册表存在`QQ`项，没有找到微信对应项。此结果核实了本机开始菜单登记身份和程序签名，但实际 Toast 的`UserNotification.AppInfo.AppUserModelId`是否相同仍须以事件验证；通知内容及私聊归属尚未检查。[通知监听API](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)通过通知的`AppInfo`提供来源应用信息，AUMID是应用标识。[AppInfo.AppUserModelId](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.appinfo.appusermodelid?view=winrt-28000)
- 小K本机设置中的微信/QQ监听开关仍关闭，两个发布者列表仍为空；没有请求Windows通知权限、启用监听或读取任何通知正文。不得把显示名、图标或快捷方式候选直接当作已验证的通知事件身份。
- 通知监控调用应用适配器时，`conversationId`、发送者和 `isPrivate` 均为未知值。`MessageNoticePolicy` 在读取正文前因私聊状态未知而返回，因此目前不会将真实通知正文送入模型。正文缺失时的“手动打开会话、不切窗”提示已经有策略和合成检查，但尚未对当前两客户端完成 30 条/应用的真实验收。
- `message.send.v1` 只能展示最终平台/收件人/正文预览，随后以 `SEND_ADAPTER_UNAVAILABLE` 结束；没有连接微信或 QQ 的发送器，不能发送。
- 初始外发范围仍仅 QQ 显示名 `K` 与微信显示名 `L`。稳定账号身份尚未独立核实；本次未联系任何人。

### 可行性与不打扰结论

截至本记录，未在腾讯官方公开资料中确认可直接操控个人微信/QQ桌面账号收发消息的 API。腾讯公开 IM 文档描述的是开发者将 SDK/REST API 集成到自有应用中，不是个人桌面账号的客户端桥接。[腾讯开放平台](https://open.tencent.com/)、[腾讯云即时通信 IM 产品概述](https://cloud.tencent.cn/document/product/269/1498)

Windows 通知监听需要 MSIX 身份与用户授权；它只能提供系统收到的通知，不自动提供可证明的私聊会话元数据。[Windows 通知监听 API](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)。微软桌面 UI 自动化指南指出，常规自动化动作要求目标窗口在前台，或会自动把窗口带到前台；部分 UIA 控件操作可尝试关闭自动聚焦，但支持情况取决于控件和应用。[桌面自动化说明](https://learn.microsoft.com/en-us/power-automate/desktop-flows/desktop-automation)、[UI Automation AutoSetFocus](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation2-get_autosetfocus)

因此，不承诺后台静默发送。后续只有在公开 API 或当前客户端控件确实支持后台读写、目标身份可稳定识别、发送回执可独立验证，且另一应用持续输入时无前台/鼠标/键盘/剪贴板变化，才将相应动作登记为后台能力。若只能前台操作，必须作为单独的前台等待任务呈现；若客户端不支持可靠识别则反馈不支持。不得读取客户端数据库、注入进程或逆向私有协议。

**R4 闸门：未通过。** 阻塞项是 AUMID/通知格式与私聊归属实测、K/L 稳定身份绑定、可靠发送方法及不抢前台与回执验证。
