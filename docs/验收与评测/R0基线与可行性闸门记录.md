## 微信与 QQ 能力闸门

已读本机进程版本快照：微信 `4.1.15.13`、QQ `9.9.30.48762-6a73892f`。版本随更新变化，后续验收需重新读取。

### 已有实现

- WPF/MSIX 清单声明 Windows `userNotificationListener` 能力；监控按配置的发布者 AUMID 先过滤，仅处理新增 Toast，并有有界去重队列、权限/锁屏复核和状态反馈。
- 当前默认设置没有已核实的微信/QQ发布者 AUMID。用户通知授权也未实际请求。不能因某个程序名或图标相似就信任其通知来源。
- 通知监控调用应用适配器时，`conversationId`、发送者和 `isPrivate` 均为未知值。`MessageNoticePolicy` 在读取正文前因私聊状态未知而返回，因此目前不会将真实通知正文送入模型。正文缺失时的“手动打开会话、不切窗”提示已经有策略和合成检查，但尚未对当前两客户端完成 30 条/应用的真实验收。
- `message.send.v1` 只能展示最终平台/收件人/正文预览，随后以 `SEND_ADAPTER_UNAVAILABLE` 结束；没有连接微信或 QQ 的发送器，不能发送。
- 初始外发范围仍仅 QQ 显示名 `K` 与微信显示名 `L`。稳定账号身份尚未独立核实；本次未联系任何人。

### 可行性与不打扰结论

截至本记录，未在腾讯官方公开资料中确认可直接操控个人微信/QQ桌面账号收发消息的 API。腾讯公开 IM 文档描述的是开发者将 SDK/REST API 集成到自有应用中，不是个人桌面账号的客户端桥接。[腾讯开放平台](https://open.tencent.com/)、[腾讯云即时通信 IM 产品概述](https://cloud.tencent.cn/document/product/269/1498)

Windows 通知监听需要 MSIX 身份与用户授权；它只能提供系统收到的通知，不自动提供可证明的私聊会话元数据。[Windows 通知监听 API](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)。微软桌面 UI 自动化指南指出，常规自动化动作要求目标窗口在前台，或会自动把窗口带到前台；部分 UIA 控件操作可尝试关闭自动聚焦，但支持情况取决于控件和应用。[桌面自动化说明](https://learn.microsoft.com/en-us/power-automate/desktop-flows/desktop-automation)、[UI Automation AutoSetFocus](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation2-get_autosetfocus)

因此，不承诺后台静默发送。后续只有在公开 API 或当前客户端控件确实支持后台读写、目标身份可稳定识别、发送回执可独立验证，且另一应用持续输入时无前台/鼠标/键盘/剪贴板变化，才将相应动作登记为后台能力。若只能前台操作，必须作为单独的前台等待任务呈现；若客户端不支持可靠识别则反馈不支持。不得读取客户端数据库、注入进程或逆向私有协议。

**R4 闸门：未通过。** 阻塞项是 AUMID/通知格式与私聊归属实测、K/L 稳定身份绑定、可靠发送方法及不抢前台与回执验证。
